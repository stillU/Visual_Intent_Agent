# 05 · RAG 接入后的评测准备（暂不执行真实批次）

顺序由用户决定：先完成 RAG，再评测。此文件不是当前运行正式评测的授权。

## 启动条件

- 01～04 工程验收通过，生产知识实际审核完成，三项后置修复继续通过。
- 固定代码快照、知识 JSONL 与哈希、检索/分词/渲染版本、Provider 参数；真实模型别名与来源适用性核实。
- 用户确认本次调用预算、样本数量及人工评审安排后，才运行真实批次。
- 另建 v0.4 协议/数据/标注/manifest/结果目录，保留全部旧冻结物；先明确改善阈值、延迟成本上限和缺失处理，不能看结果后定标准。

## 最小对照

B：修复后的同一系统关闭知识检索；C：同一代码开启知识检索。先做 B/C 消融，Direct LLM 的 A 组可随后单独补充，不把未做 A 组比较描述成完整 Gate A 通过。

为隔离知识选择影响，B/C 使用内容相同的已确认 Intent、Execution 与委托范围，分别建立新会话、无已有 active Realization。保留各自真实确认，不复制不合法跨会话 IDs。冻结相同的基线选择 seed 映射供评测夹具使用，或记录并平衡其差异：当前旧选值依赖 revision ID，不同随机 ID 可能造成非 RAG 差异，不能忽略。产品默认选值算法不为评测作弊而改动。

样本必须包含适用的委托决策、明确值/PIN 的负对照、无命中回退、多轮修改及知识注入攻击。知识编写/检索调试集与最终保留测试集分离；禁止把最终样本答案放进知识库。

## 分层记录

- 安全：未授权修改、确认绑定、PIN、不可变历史、来源完整性。
- 检索：适用性、有效命中、采用/回退比例、冲突建议；不能只报命中次数。
- Prompt：覆盖、保留、完成率；使用修复后的 harness 身份。
- 图片：同用户阶段盲配对，展示用户约束，区分遵守要求与主观偏好；不要仅按脚本轮序强行配对。
- 成本：查询耗时、总耗时、模型调用与失败、知识审核维护量。

知识可产生的收益预计集中在委托实现，明确指定字段的负对照应不变；若只在少数范围有效，如实限定结论，不泛化为全面提高语义理解。结果不充分就记录证据不足，不为了“用上 RAG”扩大知识库或美化指标。
