# MVP v0.3 更改书 001：纠正评测与语义边界，完成可用版本

日期：2026-09-15。状态：原实施计划，执行顺序已由 [更改书 002](REVISION_002_BUILD_FIRST.md) 替代；本文件保留语义与评测修订依据，不表示各项已完成。适用起点：Step 06 patch 002 后。

## 1. 目标与优先级

以最短可验证路径完成 v0.3：保留现有实现，纠正已经发现的评测失真和明显语义误判，完成一次正式复评，再交付最小 CLI。

本更改书优先于原 v0.3 Step 06～08 中与其冲突的条款。原任务书和旧评测文件保留为历史依据。允许修正错误规则、标注和指标，但必须建立新版本并记录理由；禁止覆盖旧结果或把新旧评分直接宣称为同口径提升。

“最小修改”以能解决真实问题为条件。若提示词无法保证关键状态安全，允许增加最小确定性检查；不为保持文件不变而保留已确认错误。

最终完成标准分两项：工程验收通过；Gate A 有证据充分的 Go / No-Go 结论。无充分证据时记录“证据不足”，不能写成产品假设被否定，也不能据此发布 Go。CLI 发布仍以 Gate A 为 Go 为前提。

## 3. 最短执行链

R0 固化快照 → R1 同步修正语义、评测与恢复行为 → R2 小样本验收 → R3 一次正式复评 → R4 最小 CLI。

不重新实施原 Step 01～05，不新增通用评测平台；沿用 Baseline、Runner、Repository、盲评工具和现有模型接口。

### R0：固化现有成果

1. 将当前 Step 01～06 的源码、测试、冻结输入、交接记录整理为一个可回滚提交；提交前核对实际变更范围。
2. 保留旧图片、SQLite 和 Run 记录，建立文件哈希清单及可恢复的存储位置；大文件不混入源码提交。
3. 新建 `evaluation/protocol_v0_3_r1.md`、`configs/gate_a_v0_3_r1.json`、`frozen_manifest_v0_3_r1.json`。旧清单和旧测试继续验证旧文件。
4. 增加修订日志：旧规则、已确认错误、修正语义、受影响案例、测试方式。不以旧系统输出自动生成答案。

验收：新开发者能从提交和产物清单复原当前检查点；真实实验不使用只有包版本的身份标识。

### R1-A：修正少量明显不成立的产品语义

允许修改：`intent_engine/prompts.py`、`feedback/engine.py`、`policy/decision_policy.py` 及对应语义测试。已有执行上下文接线、中文匹配支持、不可变状态与确认绑定继续复用。

1. 数量：中文明确数词“一只/两只/三位”允许输出对应整数；“猫在睡觉”不默认数量。英文冠词 `a/an` 不强制写结构化数量，英文 `one/two` 可写。文本中已有的数量描述必须保留。
2. 地点：“在沙发上/壁炉旁”可以作为动作或场景细节保留；不能推导用户没说的房间。明确“地点是客厅”必须提取。不要要求所有用户用固定句式才能表达地点。
3. 移除“室内自然光必然矛盾”的阻断；摄影与水彩质感允许混合；远景不等于宽高比要求。不能确定是否矛盾时保留用户表达；不建设新的冲突推理引擎。
4. 保留可以明确证明的字段冲突检查；对摄影棚+海滩等可能表示布景的组合，不能仅凭词表强制阻断。明确冲突的新标注必须说明为什么两个要求不能同时成立。
5. 保留局部 CLEAR/PIN 约束。对“其他不变”“去掉主体”的歧义表达允许澄清；不把某一种人为路径拆法作为唯一自然语言真值。用户明确指定局部修改时，其他字段保持不变。
6. 更新 prompt 与 policy 的版本号。规则语义已改变，不能继续使用原 `policy.v1` 冒充同一策略。

测试：优先验证输入→Delta/Issue/最终状态的行为；提示词字面量测试只保留版本与关键协议约束。Fake LLM 不能验证真实语言理解，相关结论在 R2 真实探针中验证。

原测试若固化了本节已确认的错误语义，应同步修正预期并记录理由；不可变状态、PIN、来源校验等安全不变量测试不得为通过测试而放宽。

条件性升级：若真实探针仍出现越权破坏性修改，新增轻量“变更范围待确认”分支：展示拟删除/保护路径，明确确认前不应用歧义 CLEAR/PIN，不自动扩大 EvidenceRef schema，也不依靠同一 LLM 自报路径作为确定性授权证据。其公共合同、重试与过期确认测试必须随实现交付。

### R1-B：用新口径修正评测

允许修改：`evaluation/runner.py`、`reporting.py`、`metrics/prompt.py`、`image_review.py` 和相应测试；保持旧输入与原始结果可读。

1. 从旧 22 例生成 `fixtures/core_v0_3_r1.jsonl` 与对应 annotations；只修正 R1-A 涉及的答案和必要对话轮次，记录 parent_case_id 和更改原因。未受影响案例逐字保留。
2. Preservation 只比较实际产生的相邻有效 Prompt 中“仍被要求保留”的属性。新增按路径关联的保留词组，跨澄清轮累计合法修改路径；用户明确改掉的旧值不算丢失。
3. 正常澄清/拒绝无 Prompt 标为不适用；应生成而失败单独记失败与完成率。报告同时给出可比较对数、正常未生成、失败未生成，不能通过删除分母美化结果。
4. 脚本与状态偏离时保留首次根因；无法执行的后续轮记 `blocked_by_prior_failure` 并关联来源。案例失败仍进入总完成率。不要把后续每一轮重复记成独立根因，也不要自动把澄清答案改送反馈入口。
5. 修订集使用预先冻结的相同用户消息给 A/B；已有 answer_variants 改为预先选定的输入，动态回答仅留给独立交互诊断。必要时调整脚本让问题顺序可变化，但不向模型泄露标注答案。
6. 盲评按“用户请求已推进到同一阶段”配对，呈现完整相关用户文本、必须保留内容和目标改动。允许 A/B 不同澄清轮数；无法匹配时单独统计。自动确认仅是实验代理，不算验证了真实用户确认体验。
7. 保留自由偏好与指令遵守两个独立评分。PIN 情况下偏好删除后的图片可以记录，但不能将其当作遵守保护约束的成功。
8. 关键词违例改名为 `forbidden_keyword_hit`；来源校验是否失败单独报告。新旧指标版本分别标识。
9. Runner 增加 `--manifest` 选择新清单，由清单解析协议、配置、数据集及标注；仍默认支持旧清单。正式运行必须校验所有哈希，不能通过关闭校验导入外部数据。
10. 真实运行默认产物路径改为 `outputs/evaluation_runs/`，解决默认二进制产物与 evaluation UTF-8 扫描的冲突。正式模式检查工作区源码/评测输入干净并记录完整 commit；允许诊断模式，但结果显式标记不作为正式 Gate。

最小实现方式：保留旧评分函数，通过协议版本选择 r1 函数；复用现有结果结构，对新增字段提供兼容默认值。旧 Run 使用 r1 重算时另写报告，不覆盖原报告。输入或标注已经改变的案例不能靠重算变成新协议正式样本。

### R1-C：超时恢复与重试记录

1. 复用现有 Adapter 和引擎的重试上限；不新增第三层自动重试，不提高预算来掩盖失败。
2. 重试耗尽后保留用户消息、原 Intent 和已存在 PIN，返回明确“本轮未处理成功”；不将空理解结果当成新的澄清需求推进会话。优先复用现有 recoverable failure；仅在现有合同无法表达时增加向后兼容字段。
3. 同一请求重试只能在成功后应用一次 Delta。测试覆盖 timeout→成功、连续 timeout、PIN 请求失败后恢复、过期请求不能应用到新 revision。
4. 记录 A/B 各自引擎调用次数、耗时和失败，说明 Adapter 内尝试次数是否可观测；未知值不能写成 0。允许两系统内部策略不同，但不得声称总调用预算一致。
5. 若必须更换 Provider、超时或模型参数，则建立另一份配置和 Run，A/B 同时切换，重新实验；不能与旧配置结果拼成一轮。

验收：失败可恢复、状态不越权、调用有界；真实健康探针失败会终止后续付费批次并保留记录，不反复试到成功才开始计数。

### R2：最小验收批次

先运行全量离线测试和新版清单校验，再做一次固定真实探针批次。探针不生成图片：真实 LLM + Fake Image 使用现有接口装配合法会话。

固定 12 个探针：一只/两只/无数量各 1；明确地点/自由处所各 1；室内自然光/摄影水彩质感/方图远景各 1；局部 CLEAR/局部 PIN/UNPIN 后修改/明确字段冲突各 1。

每个探针仅运行一次完整场景，允许既有有界内部重试；记录全部请求和结果。任何破坏性越权、状态损坏、明确要求丢失阻断 R3。Provider 耗尽则记录基础设施阻断，修复或更换配置后整批新建 Run，旧记录保留。

验收报告必须分别列出确定性回归结果和真实语义探针结果；不以全部 pytest 通过代替真实验收。

### R3：一次正式复评

1. R2 通过后冻结 r1 代码、协议、输入、标注和人工评价规程。
   冻结前在 r1 协议中明确改善指标、最小实际改善幅度、等待/澄清成本上限及缺失结果处理方式，优先继承仍有效的旧阈值；未明确这些判定规则不得开始正式复评，也不得看到结果后补定阈值。
2. 修订核心集 22 例 × 2 次 × A/B；沿用现有生成链路和盲评工具。两次重复保留，但不将重复当作独立用户样本。
3. 在同一实验时段交错运行 A/B；不复用旧 A 结果与新 B 拼接，以减少 Provider 时间差异。
4. 每个样本逐层报告 L1 状态、L2 理解、L3 Prompt、L4 图片；单列完成率、澄清次数、等待时间和调用量。
5. 人工盲评至少两名独立评审；分歧保留，客观约束分歧依据原始用户要求裁定。只有一名评审时报告探索性结果，不能写成稳定用户偏好证据。
6. 原首轮按旧协议保留为历史诊断；正式 A/B 结论只比较同一 r1 协议下的 A 与 B。

Go：L1 全部通过、没有未解决的破坏性越权；至少一项图片修改效果或用户偏好有可复现改善，且等待与澄清成本可接受。用逐案例分布、有效样本数和不确定性支持结论，禁止临时降低阈值。结果接近或缺失较多时为证据不足，不无限补丁循环。

No-Go：出现未解决的核心状态缺陷，或有足够同口径证据表明增加的复杂度没有带来收益。输出下一版本问题清单并停止本轮扩展。

### R4：最小 CLI

Gate A Go 后执行。新增 `visual_intent_agent/__main__.py` 与一个轻量 CLI 模块，连接现有 WorkflowService、ReviewService、GenerationPipeline 和 Repository。

操作仅包含：新会话、输入需求、回答澄清、查看变更并确认、生成、查看输出路径、反馈、退出。超时显示本轮未成功并允许显式重试；确认摘要必须能被用户阅读，不能照搬 Runner 自动确认。

验收：一个完整正常流程、一个多轮局部修改、一个超时恢复场景，经 Fake Provider CLI 测试通过；真实使用记录至少包含一次重新确认后生成。更新简短运行说明及版本发布记录。

## 4. 外部数据：小规模补充，不阻塞核心复评

首批仅选两个来源：COCO-CN 人工中文描述 20 条、T2I-CompBench 验证集按颜色/形状/材质/空间/非空间/复杂组合各 5 条，共 50 条。固定来源 revision、样本 ID、文件哈希和抽样种子。

- COCO-CN：https://github.com/li-xirong/coco-cn
- T2I-CompBench：https://github.com/Karine-Huang/T2I-CompBench

原文用于独立的覆盖与图片语义评估；没有 IntentDelta/PIN 标签的样本不能直接评 L1/L2。需要对话改写时记录原文、改写规则、人工标注，称为“派生测试”，不冒充官方基准成绩。缺少必需意图项时，预先冻结相同补充信息并提供给 A/B，不由评测器临时猜测。

当前 Schema 无法直接表达的多对象关系另列能力边界，不为跑基准扩展 domain。MagicBrush 暂缓：当前产品从文本重新生成图片，没有参考图编辑接口，不能直接与其目标图评像素保持。

外部测试使用独立 manifest 和结果目录，先跑文本层，再选预先固定的 10 条做图片诊断。不纳入当前 Gate 分母。许可证及再分发要求随来源保存，只提交合法允许的数据或样本索引。

## 5. 交付、顺序与停止点

| 顺序 | 实施范围 | 交付 | 下一步条件 |
|---|---|---|---|
| R0 | 快照与版本记录 | 检查点 commit、产物清单 | 能还原现状 |
| R1 | A/B/C 三项修正 | r1 协议/数据/标注、最小代码修改、回归测试 | 原始数据可读，新测试通过 |
| R2 | 固定探针验收 | 12 探针记录、阻断项清单 | 语义与恢复验收通过 |
| R3 | 正式评测 | r1 A/B 报告、盲评、Go/No-Go/证据不足 | Go 才进入 R4 |
| R4 | CLI 接线 | 可运行入口、使用说明、发布记录 | v0.3 完成 |

每步交接写入 `docs/handoffs/v0_3_r1_R<N>_handoff.md`，包含 commit、修改理由、测试、原始记录位置、遗留风险、能否进入下一步。R1 的 A/B/C 由同一实施负责人顺序完成，减少共享接口返工。

预计代码与协议修订约 2～4 个工作日，探针与复评另受 Provider 和人工评审时间影响，CLI 约半天至一天。这是范围估算，不是完成承诺。最长路径在真实调用与评分，因此优先修复会污染结果的口径问题，再消费图片预算。

## 6. 直接派发说明

请执行本更改书 R0～R2，先阅读当前实现和所有 Step 06 补丁记录。保留既有工作区成果，按步骤形成检查点；修正已确认的语义、评分与故障恢复问题，不重写系统。旧冻结文件继续保留，所有语义和评分变化进入 r1。R2 验收通过后按 R3 冻结一次正式复评；有阻断项即交付证据和最小后续动作。Gate A 未 Go 时不发布 R4。除有独立语义依据并记录理由的纠错外，不得迎合系统输出修改期望值，也不得隐藏失败或反复重抽样让评测过关。
