# Step 06：证据驱动的定向修正

## 目标

仅针对 Step 05 已确认的核心失败实施最小修复。所有修改必须有失败案例、影响指标和预期行为作为依据。

## 启动条件

- Step 05 结论为 `Conditional Go`；或
- Step 05 为可修复的 `No-Go`，且报告明确建议进行一次受限修正。

若报告没有给出可验证的修正目标，本步骤不得启动。

## 实施流程

1. 从 `failure_catalog.jsonl` 选择需要修复的失败类别，不新增未记录问题。
2. 为每项修复先写回归测试，固定失败案例和期望行为。
3. 标出受影响模块、现有不变量、公开合同和 Artifact 兼容性。
4. 实施满足测试的最小修改；优先修正规则或边界，不增加架构层。
5. 运行受影响测试和全量离线测试。
6. 用冻结评测 Runner 做诊断性复跑，但不得据此修改数据集或评分口径。
7. 记录每项修复与失败案例、代码变更和指标变化的对应关系。

## 允许范围

- `intent_engine`、`validation`、`policy`、`workflow`、`prompt_engine`、`feedback` 或 `realization` 中被证据直接指向的最小修改。
- 对应单元测试、回归 fixture 和必要的架构修订记录。

## 交付物

- 针对失败案例的回归测试与最小实现修改。
- `evaluation/reports/fix_traceability.md`
- `docs/handoffs/v0_3_step_06_handoff.md`

## 验收条件

- 每个代码改动都能追溯到 Step 05 的失败案例。
- 新回归测试修复前失败、修复后通过。
- v0.2 核心不变量和全量离线测试继续通过。
- 不修改冻结数据集、Baseline A 或正式评分实现。

## 禁止范围

- 不实现 KnowledgeEngine、RAG、参考图、Web UI、多模型或多 Agent。
- 不为了单个样本硬编码答案。
- 不顺带重构无关模块。
- 不在本步骤自行宣布最终 Go。
