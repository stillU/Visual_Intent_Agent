# Step 03：独立语料发布与真实采用验证

前置：Step 02 对将发布的精确提案已有真实批准，来源复用条件已落实。未满足时可做临时夹具测试，但本步骤不能标完成。

## 发布方式

1. 在新的 `knowledge_base/v0.5/` 创建不可变发布快照；若目录已存在先核实，不覆盖既有版本。首个发布 corpus_version 使用 `v0.5-approved-1`，后续变化产生新版本/快照，不悄悄覆盖。
2. 保留 `knowledge.v1`、`keyword.v1`、`lexical.v1`，除非发现必须变更且先获用户批准。不为新内容升级数据库 Schema。
3. 发布目录仅收录本次获批单元；草稿/证据卡不混进生产 JSONL。按现有合同维护 ID/version、完整来源、真实审核字段、content_hash 与 manifest 文件哈希/条数。不得在同一语料内重复 knowledge_id。
4. 随包记录许可/署名/修改说明、对应审核决定、版本说明、适用限制及复建步骤。v0.4 原快照和用户数据库不变。若合同不能容纳某来源的必要信息，用随附文件补齐可追溯关系，不弱化合同校验。
5. 使用现有加载器加载整个目录并核验 `build_units()`。CLI 使用既有 `--rag --knowledge-dir knowledge_base/v0.5` 选择新库；保持默认 RAG 关闭及原默认路径不变。文档应说明该选项用于明确选择语料，不直接启动真实运行作验收。

## 必须使用最终语料做离线集成

CLI 的 `--demo --rag` 使用内置演示语料，且不接受外部 knowledge-dir，因此不能用它冒充生产语料验收。复用现有测试依赖注入接口，加载最终发布目录，连接临时真实 SQLite Repository 与 Fake Interpreter/Image Provider；不新增访问真实服务的“验证捷径”。

每条获批规则至少建立一个从规则适用条件推导的可达正例和一个条件不符/保护边界反例。这是规则验证用例，不是保留集质量评测。三个路径都需有至少一次如下证据：

- 从显式确认且用户委托的上下文进入检索；无 active Realization，候选合法；检索命中与消费者 adopted 决定一致。
- 采用结果进入实际 Realization 和 PromptArtifact；关联 Bundle、单元 ID/version/hash、语料版本、适用性快照可从数据库读回。
- 至少一个受控对照上下文中，RAG 选值与关闭 RAG 的确定性基线不同，且差异只在授权范围。只证明建议能影响产物，不宣称更优；不能为了制造差异调规则或放宽安全边界。
- 已有 active Realization 优先复用；原 Prompt 重试不重新检索。知识快照切换不改变旧生成依据或重写历史。

若合法数据恰与基线相同，应先寻找另一个合法工程上下文；无法证明差异则报告证据缺口，不伪造成功。采用状态与图像质量仍分开。

## 验收

最终快照可加载、获批数准确、真实批准证据可追溯；三路径正例及保护反例通过；RAG 无额外 LLM/网络调用；普通数据库读写和历史兼容不变。新缺陷若需改变确认/PIN/领域合同，先停并请求裁定。
