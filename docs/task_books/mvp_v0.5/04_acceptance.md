# Step 04：集中离线验收与版本交接

## 验收矩阵

| 范围 | 必须验证 |
|---|---|
| 真实内容 | Step 03 最终语料正例实际 adopted，规则与版本可追溯；不是仅演示夹具 |
| 用户控制 | 明确值、PIN、未确认、非委托字段不被知识覆盖 |
| 适用性 | 条件缺失/不符、模型不匹配、draft/rejected、缺少快照及内容哈希不符均不得被新采用 |
| 回退与错误 | 无可用知识、无命中、并列冲突按现行合同回退；非法目录/损坏语料遵循既有 CLI 错误合同，不伪报启用 |
| 数据库 | Session/Intent/确认/Realization/Prompt/Generation/反馈原有读写，以及知识审计关联正确；旧库迁移与旧 payload 可读 |
| 失败与重试 | Bundle 写库失败受控失败且图片调用为零；全库失败如实报告；Provider retry 复用原 Prompt、零重新检索 |
| 关闭 RAG | 不加载语料、不检索、不创建 Bundle，业务行为与基线一致 |
| 可复现性 | 相同输入和快照结果稳定；切换新语料不改历史记录与 active Realization |
| 数据隔离 | 来源许可、固定版本、分组与派生标注可追溯；保留池未用于知识编写或调参 |

复用现有断言；只补缺失覆盖，不为了数量重写测试。项目派生用例目标为三路径各十种场景，具体分类见资源包；成功采用需要最终生产快照，恶意/冲突/未审核等反例可使用明确标注的合成 fixture。

## 运行与证据

执行前核实 pyproject 中 smoke 默认排除及测试是否含外部访问，全部使用 Fake 与临时数据库，不读取真实凭据。开发阶段运行相关局部测试，集成完成后运行一次 `uv run pytest -q` 与 `git diff --check`；失败修复后做必要复测。记录实际命令、退出码、通过/失败/跳过数，不复制 v0.4 的旧数字当新结果。

运行输出不能仅表明“全绿”：还需列出最终语料版本/哈希、每路径实际采用的单元、数据库追溯证据、数据准备覆盖及真实审核记录。未获审核则说明仅夹具工程回归可执行，真实内容采用验收待定。

## 最终交付

写 `docs/handoffs/v0_5_release_handoff.md`，包含：

1. 实际 HEAD/工作区与本批文件范围，保护了哪些旧数据/旧快照。
2. 数据准备：各来源完成度、许可、实际数量、分组与未完成项。
3. 知识：draft/approved/rejected 与本次发布数量、三路径覆盖、真实审核入口。
4. 工程：定向与全量测试、生产语料采用证据、普通数据库及历史兼容结论。
5. 限制：词法检索边界、未核实模型别名、未支持语义、不可推断的质量收益。
6. 版本结论：完成 / 部分完成 / 等待审核，逐项对应 README 的完成标准；正式评测明确写未执行。
7. v0.6 输入：候选语料快照、来源/划分清单、工程基线与待制定评测协议。后续协议应另行确定预算、模型/Provider 版本、指标和停止条件，本版不提前批准。

更新任务索引/架构中与实际状态相关的最小内容，主 README 仍保持简洁项目介绍，不重新塞入实施步骤。未获要求不提交、推送、删除历史或开始下一版本。
